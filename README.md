# Proofline

Proofline은 Codex가 요청받은 작업 범위를 끝까지 지키고, 직접 확인한 결과를 바탕으로 완료 여부를 보고하도록 돕는 플러그인입니다.

작업이 길어지면 처음 요청의 세부 조건을 빠뜨리거나, 확인하지 않은 부분까지 끝났다고 보고하기 쉽습니다. 대화 중 발견한 버그나 후속 작업도 다음 작업으로 이어지지 않고 잊히곤 합니다. Proofline은 대화에 적용할 공통 기준과 작업별 스킬, 프로젝트에 남는 기록으로 이런 누락을 줄입니다.

## ✨ 주요 기능

- **대화와 결과물 품질 관리**: 요청 범위, 수정 권한, 검증 근거를 확인하고 응답 방식을 `normal`, `focus`, `core`으로 전환합니다.
- **기획부터 구현까지**: 아이디어를 기획서와 구현 명세로 정리하고, 구현·검증·독립 검토로 이어갑니다.
- **리팩터링과 코드 이식 검증**: 실제 구조가 바뀌었는지, 원본 동작이 보존됐는지 확인합니다.
- **프로젝트 기록 관리**: 이슈, 기획서, 구현 명세, 아키텍처 문서를 파일로 남겨 다음 작업에서 참고합니다.
- **통합 대시보드**: 여러 프로젝트의 작업 기록과 아키텍처 문서를 로컬 웹 화면에서 확인합니다.

## 📦 설치

### Codex CLI에서 설치

Proofline 마켓플레이스를 추가한 다음 플러그인을 설치합니다.

```bash
codex plugin marketplace add semisemil/codex-proofline
codex plugin add proofline@proofline
codex
```

훅과 보조 도구를 실행하려면 Node.js 22 이상이 설치되어 있고, 터미널에서 `node`를 실행할 수 있어야 합니다. 저장소 테스트는 Windows와 Linux의 Node 22·24 조합으로 실행합니다. 기능별 요구 사항은 [호환성 및 지원 환경](docs/compatibility.md)을 참고하세요.

Codex가 열리면 다음 순서로 마무리합니다.

1. `/hooks`를 엽니다.
2. Proofline의 `SessionStart`, `SubagentStart`, `UserPromptSubmit`, `PreToolUse` 훅을 확인하고 승인합니다.
3. 새 작업을 시작합니다.

하위 에이전트에 공통 기준과 아키텍처 메모리를 연결하려면 `SubagentStart` 지원이 필요합니다. 기획부터 구현까지 자동으로 진행하는 기능에는 새 작업 생성과 독립 에이전트 실행 기능도 필요합니다.

## 🚀 빠르게 사용하기

### 공통 기준과 응답 모드

`proofline` 공통 기준은 새 작업을 시작하거나 `/clear`, `/compact`를 실행할 때 자동으로 불러옵니다. 기존 작업을 재개할 때(`resume`)는 공통 기준을 다시 불러오지 않지만, 대시보드 서버 확인과 아키텍처 메모리 연결 훅은 실행됩니다. 하위 에이전트에도 `SubagentStart` 훅으로 공통 기준을 전달합니다.

특정 요청에 공통 기준을 명시하려면 스킬 이름을 적으세요.

```text
$proofline:proofline
이 문서를 처음 읽는 사람도 이해할 수 있게 고쳐줘.
```

응답 모드를 바꾸려면 프롬프트의 첫 내용 줄에 다음 명령을 적습니다. 앞에 빈 줄이 있어도 됩니다.

| 명령 | 동작 |
| --- | --- |
| `$proofline` | 현재 모드와 기본 모드 확인 |
| `$proofline normal` | 자연스러운 일반 문장으로 응답 |
| `$proofline focus` | 짧은 구절과 줄바꿈 위주로 응답 |
| `$proofline core` | 기술적 정확성을 유지하면서 최대한 짧게 응답 |
| `$proofline default` | 새 작업에 적용할 기본 모드 확인 |
| `$proofline default <mode>` | 기본 모드를 저장하고 현재 작업에도 적용 |

초기 기본 모드는 `normal`입니다. 현재 모드는 작업별로 저장되며, 모드를 바꿔도 공통 품질 기준은 유지됩니다. 잘못된 명령을 입력하면 사용법을 안내하고 기존 모드를 유지합니다.

### 작업에 맞는 스킬 사용하기

일부 스킬은 Codex가 작업에 맞춰 불러오고, 기획·구현 시작처럼 직접 호출해야 하는 스킬도 있습니다. 적용할 기준을 분명히 하고 싶다면 아래처럼 스킬 이름을 적으세요.

책임이나 호출 구조를 바꾸는 리팩터링:

```text
$proofline:refactor-proof
사용자 설정 저장 책임을 서비스 계층으로 옮겨줘.
```

원본 동작을 그대로 유지해야 하는 코드 이식:

```text
$proofline:exact-port
이 원본 구현을 대상 프로젝트로 동작 변경 없이 옮겨줘.
```

## 🧩 포함된 스킬

### Core

공통 품질 기준, 작업 검증, 이슈 기록과 대시보드를 담당합니다.

| 스킬 | 이런 때 사용합니다 | 하는 일 |
| --- | --- | --- |
| `$proofline:proofline` | 대화와 결과물 전반 | 자연스러운 문장, 요청 범위, 수정 권한, 판단 근거 확인 |
| `$proofline:scope-integrity` | 규모가 크거나 위험하고 여러 단계로 진행되는 작업 | 합의한 목표와 필수 조건, 중간 점검, 검증 계획, 범위 변경 관리 |
| `$proofline:refactor-proof` | 책임, 의존 관계, 호출 구조, 상태 흐름을 바꾸는 리팩터링 | 실제 구조 변경과 기존 동작 보존 여부 검증 |
| `$proofline:exact-port` | 원본 동작을 그대로 옮겨야 하는 코드 이식 | 원본과 대상 비교, 사용자에게 승인받은 차이와 미확인 부분 기록 |
| `$proofline:issue-ledger` | 버그나 후속 작업을 프로젝트에 남길 때 | 현재 상태, 다음 조치, 완료 조건, 결정과 검증 근거 기록 |
| `$proofline:capability-growth` | 반복하는 수작업을 자동화할지 검토할 때 | 기존 도구와 자동화 후보 비교, 등록 전 사용자 승인 확인 |
| `$proofline:dashboard-server` | 통합 대시보드를 이용할 때 | 현재 프로젝트 등록, 실행 중인 대시보드 열기·상태 확인·종료 |

### Architecture

프로젝트 구조와 주요 결정을 문서로 남기고, 개발 중 참고하거나 갱신합니다.

| 스킬 | 이런 때 사용합니다 | 하는 일 |
| --- | --- | --- |
| `$proofline:architecture-memory-init` | 아키텍처 메모리를 처음 만들 때 | 코드와 기존 문서를 바탕으로 구조·제약·결정 정리 |
| `$proofline:architecture-memory` | 프로젝트 배경을 참고하거나 새로 결정한 내용을 남길 때 | 관련 문서 검색, 사용자 결정과 운영 환경 기록 |
| `$proofline:architecture-memory-update` | 커밋된 코드 변경을 아키텍처 문서에 반영할 때 | 마지막 확인 커밋 이후의 변경 검토와 문서 갱신 |

### Workflow

기획과 명세 작성부터 구현, 검증, 독립 검토까지 개발 단계를 이어갑니다.

| 스킬 | 이런 때 사용합니다 | 하는 일 |
| --- | --- | --- |
| `$proofline:figure-it-out` | 필요한 기획부터 구현까지 한 번에 맡길 때 | 기획·명세 작성과 검토를 거쳐 새 구현 작업 생성 |
| `$proofline:development-plan` | 아직 구체화하지 않은 아이디어를 개발 기획으로 정리할 때 | 목적, 방향, 결정 사항, 제약을 기획서로 작성 |
| `$proofline:implementation-spec` | 구현 명세를 만들거나 수정·완료 처리할 때 | 요구 사항, 완료 조건, 검증 방법, 명세 상태 관리 |
| `$proofline:tenet-me` | 기획·명세·설계가 요청 의도에 맞는지 검토할 때 | 누락된 요구 사항, 검증 방법, 추가 결정이 필요한 부분 확인 |
| `$proofline:spec-slice` | 구현할 일을 독립적으로 나눠 병렬 진행할 수 있을 때 | 필요한 경우에만 `PARALLEL.md`에 작업별 목표·범위·연결 방식 정리 |
| `$proofline:start-implementation` | 준비된 명세의 구현을 새 작업에서 시작할 때 | 모델과 추론 수준을 정하고 현재 프로젝트 폴더에 새 작업 생성 |
| `$proofline:implement` | 준비된 명세를 현재 작업에서 구현할 때 | 직접 구현, 필요한 병렬 작업 배정, 검증과 독립 검토 |

## 🔁 기획부터 구현까지

Proofline은 기획서를 **Plan**, 구현 명세를 **Spec**이라고 부릅니다. Plan에는 무엇을 왜 만들지 정리하고, Spec에는 구현할 내용과 완료 조건, 검증 방법을 담습니다.

한 번에 맡기려면 `figure-it-out`을 호출합니다.

```text
$proofline:figure-it-out
사용자 알림 설정 개선을 필요한 기획부터 구현과 독립 검토까지 맡아서 완료해 줘.
```

진행 흐름은 다음과 같습니다.

1. **기획과 명세 준비**: 별도 준비 에이전트가 필요한 단계부터 진행합니다. 방향을 정해야 하면 `development-plan`으로 Plan을 작성하고, 요구 사항이 충분히 정리되어 있으면 Spec 작성부터 시작합니다.
2. **구현 전 검토**: `tenet-me`로 Plan과 Spec을 검토하고 필요한 수정을 반복합니다. 자료만으로 결정할 수 없는 중요한 선택은 사용자에게 확인합니다.
3. **새 구현 작업 생성**: 준비된 Spec을 `start-implementation`에 전달합니다. 현재 프로젝트 폴더를 사용하는 새 작업을 만들고, 원래 작업에서는 생성 결과와 링크를 안내합니다.
4. **구현과 완료 확인**: 새 작업의 `implement`가 Spec을 읽고 구현·검증·독립 검토를 진행합니다. 구현 결과는 이 새 작업에서 확인합니다.

각 단계를 직접 호출할 수도 있습니다. 아래 예시는 각각 별도의 요청입니다.

```text
$proofline:development-plan
반복 업무를 자동화하는 내부 도구 아이디어를 개발 기획으로 정리해줘.
```

```text
$proofline:implementation-spec
PLAN-0001을 구현 가능한 명세로 정리해줘.
```

```text
$proofline:tenet-me
SPEC-0001이 요청한 내용을 빠짐없이 담고 있고, 완료 여부를 검증할 수 있는지 확인해줘.
```

```text
$proofline:start-implementation
SPEC-0001 구현을 새 작업에서 시작해줘.
```

현재 작업에서 바로 구현하려면 준비 상태가 `ready`인 Spec ID를 지정합니다.

```text
$proofline:implement SPEC-0001
```

`start-implementation`도 새 작업에 이 한 줄을 전달합니다. 구현에 필요한 요구 사항과 결정은 Spec에 담으며, 새 작업에 원래 대화 전체를 복사하지 않습니다.

병렬 진행이 도움이 될 때만 `spec-slice`로 Spec 옆에 `PARALLEL.md`를 작성합니다. 주 구현 에이전트는 독립적인 일을 하위 에이전트에 배정하고 자신이 맡은 구현도 계속합니다. 독립 검토는 매번 새 에이전트가 주 구현 에이전트와 같은 모델·추론 수준으로 수행하며, 이전 검토 결과나 구현 대화는 전달하지 않습니다.

새 구현 작업과 병렬 구현 에이전트의 모델 선택에는 [모델 선택 기준](skills/start-implementation/assets/model-routing.md)을 적용합니다. 저장소의 기본 설정은 Astra `medium`이며, 구현 방법과 검증 기준이 충분히 명확하면 Sol이나 Luna를 선택합니다. 사용자가 지정한 설정과 실행 도구의 제한을 우선합니다.

기존 `.proofline/prds/`의 PRD는 현재 개발 흐름에서 읽지 않습니다. 이전 기록을 옮겨야 한다면 [PRD → Spec 마이그레이션 안내](docs/migrations/prd-to-spec.md)를 따르세요. 진행 중인 이전 실행 기록을 자동으로 변환하거나 재개하는 기능은 제공하지 않습니다.

## 🗂️ 이슈 기록

`issue-ledger`는 버그, 일반 작업, 기능, 조사, 문서화, 유지보수 항목을 프로젝트에 저장합니다.

```text
$proofline:issue-ledger
설정 파일 호환성 문제를 이슈로 등록해줘.
```

```text
$proofline:issue-ledger
PL-0012의 진행 상황과 확인 근거를 갱신해줘.
```

처음 이슈를 등록하면 다음 구조가 만들어집니다.

```text
.proofline/
  STATE.md
  issues/
    PL-0001.json
```

이슈마다 JSON 파일 하나에 현재 상태, 다음 조치, 완료 조건, 결정과 검증 근거를 저장합니다. 상세 로그나 실험 보고서는 별도 파일로 연결합니다. 기존 Markdown 이슈도 읽을 수 있으며, 내용을 갱신할 때 검토를 거쳐 JSON으로 전환합니다.

Plan과 Spec은 각각 `.proofline/plan/<PLAN-ID>-<이름>/PLAN.md`, `.proofline/specs/<SPEC-ID>-<이름>/SPEC.md`에 저장합니다. 이슈를 지정해 기획하거나 명세를 작성하면 관련 작업을 연결할 수 있습니다.

## 🏛️ 아키텍처 메모리

아키텍처 메모리는 프로젝트 구조, 운영 환경, 제약, 주요 결정과 그 이유를 Markdown 문서로 관리합니다. 먼저 프로젝트에서 초기화를 요청합니다.

```text
$proofline:architecture-memory-init
이 프로젝트의 아키텍처 메모리를 만들어줘.
```

기본 위치는 `docs/architecture/`입니다. 코드·기존 문서·현재 대화를 바탕으로 시스템의 외부 관계와 주요 실행·저장 단위(C4 L1·L2), 필요에 따라 내부 구성 요소(L3)를 정리합니다. 사용자 결정과 운영 제약, 아키텍처 결정 기록(ADR)도 함께 관리하며, 근거가 없는 내용은 미확인으로 남깁니다.

초기화에 성공하면 `.proofline/architecture.json`에 문서 위치를 저장합니다. 이후 이 연결이 있는 프로젝트에서만 훅을 통해 메모리 스킬을 안내합니다. 개발 판단에 필요한 부분을 검색해 읽고, 앞으로도 참고할 결정이나 운영 정보가 생기면 관련 문서에 반영합니다. 읽기 전용 요청에서는 문서를 수정하지 않습니다.

커밋된 코드 변경을 문서에 반영하려면 별도로 갱신을 요청합니다.

```text
$proofline:architecture-memory-update
마지막으로 확인한 커밋 이후의 변경 사항을 아키텍처 문서에 반영해줘.
```

갱신 시에는 마지막 확인 커밋부터 시작 시점의 `HEAD`까지 변경 사항을 검토합니다. 미커밋 변경은 섞지 않으며, 중간에 중단되면 저장한 초안과 진행 상태를 이용해 이어서 처리합니다.

문서 검색은 별도 DB나 임베딩 없이 로컬 Markdown을 사용합니다. 필요한 부분만 읽으므로 매번 모든 문서를 대화에 넣지 않습니다. 훅을 지원하지 않는 환경에서는 `architecture-memory`를 직접 호출할 수 있습니다. 초기화와 Git 변경 반영은 직접 요청해야 하며, 모든 대화를 자동으로 기록하는 기능은 아닙니다.

## 🖥️ 통합 대시보드

대시보드는 `127.0.0.1`에서 실행되는 로컬 서버입니다. 홈(`/`)에서 작업 기록(`/dashboard`)과 아키텍처 문서(`/architecture`)를 선택하고, 등록된 프로젝트를 전환해 볼 수 있습니다. 아키텍처 화면은 문서와 마지막 확인 커밋, Mermaid 다이어그램을 읽기 전용으로 표시합니다.

이슈·Plan·Spec을 저장하거나 아키텍처 메모리를 초기화하면 해당 프로젝트를 등록합니다. 서버는 `SessionStart` 훅이 상태를 확인해 시작합니다. 별도 서버 패키지를 설치할 필요는 없습니다.

| 명령 | 동작 |
| --- | --- |
| `$proofline:dashboard-server add` | 현재 폴더에 `.proofline/`이 있으면 프로젝트 등록 |
| `$proofline:dashboard-server open` | 실행 중인 서버를 확인하고 대시보드 열기. 서버가 중지되어 있으면 시작하지 않음 |
| `$proofline:dashboard-server status` | 실행 주소, 서버 식별 정보, 버전 또는 중지 원인 확인 |
| `$proofline:dashboard-server stop` | 실행 상태와 실제 서버가 일치하는지 확인한 뒤 종료. 프로젝트 등록은 유지 |

프로젝트가 목록에 없으면 해당 프로젝트 폴더에서 `add`를 호출하세요. 이 명령은 프로젝트 파일을 새로 만들거나 다른 폴더를 검색하지 않습니다.

작업 기록 화면은 표시 중일 때 30초마다 변경을 확인하고, 탭으로 돌아오면 한 번 더 확인합니다. `다시 읽기`를 누르면 선택한 프로젝트의 원본 파일을 다시 읽습니다. 기존 `.proofline/dashboard/`의 정적 화면은 그대로 열 수 있지만, 새 기록에서는 이 폴더를 만들거나 갱신하지 않습니다.
