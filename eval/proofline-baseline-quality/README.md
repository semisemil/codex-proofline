# proofline-baseline-quality 평가

`proofline-baseline-quality`가 Codex의 기본 작업 품질에 어떤 차이를 만드는지 확인합니다.

같은 사용자 프롬프트를 Proofline 플러그인이 없는 격리 환경과 플러그인 및 `SessionStart` hook이 적용된 격리 환경에서 각각 수행하고, 의미 보존과 작업 범위, 실제 파일 변경 및 결과 보고를 비교합니다. 두 조건은 같은 프롬프트 파일을 공유하며 Proofline 사용 또는 금지 지시를 넣지 않습니다.

## 실행 범위

평가 세트는 총 12개로 구성되어 있습니다. 사용자 맥락 이해, 출력 언어와 표현 압축, 권한과 모호성 처리, 근거 기반 검토, UI 정보 설계와 코드 구현을 함께 확인합니다.

저장소의 `eval` 폴더에서 다음 명령을 실행합니다.

```powershell
npm install
npm run eval:validate
npm run eval:smoke
```

작업 모델은 `gpt-5.6-sol`, 추론 강도는 `medium`입니다. 빠른 점검은 Codex 작업 실행 24회로 구성됩니다. 세 번 반복하려면 `npm run eval:full`을 사용합니다. 작업 결과를 생성한 뒤 `npm run eval:judge`를 실행하면 저장된 `full.json`을 사용해 상대평가만 수행합니다. 결과 화면은 `npm run eval:view`로 엽니다.

공개 결과 파일은 전체 실행과 상대평가가 끝난 뒤 `npm run eval:publish`로 생성합니다. 로컬 절대 경로와 중간 실행 기록을 제외한 `summary.md`, `metadata.json`, `result.json`만 `results/published/<날짜>/`에 저장합니다. 사례마다 답변 길이 증감, 핵심 기준 통과와 최종 비교 선택을 함께 기록하며, 길이만으로 품질을 판정하지 않습니다. `results/local/`은 Git에 포함하지 않습니다.

상대평가는 핵심 기준을 먼저 적용합니다. 한쪽만 통과하면 그 결과를 선택합니다. 둘 다 통과하면 응답 사례는 최종 응답, 사례 04는 후보별 독립 의미 판정, 사례 09~12는 실제 변경 artifact를 사용합니다. `gpt-5.6-sol` 평가자는 추론 강도 `medium`으로 순서 교차 비교하며, 두 순서의 승자가 다르면 동점으로 처리합니다. 표현 압축은 두 응답이 모두 의미 PASS인 반복만 길이 비교에 포함합니다.

평가 기준만 수정한 뒤 이미 저장된 원시 결과를 다시 판정할 때는 다음 명령을 사용합니다.

```powershell
npm run eval:regrade
```

재판정은 `results/local/full.json`의 모델 응답과 증거를 다시 사용하므로 Codex 작업을 새로 실행하지 않습니다. 원본 결과는 덮어쓰지 않으며 `full-regraded.json`과 `full-regraded-summary.md`를 별도로 만듭니다. 상대 우열은 같은 원시 결과와 재판정 기록에 연결된 스키마 3 상대평가만 재사용합니다. 없으면 기존 최종 응답 기반 판정을 대신 쓰지 않고 미판정으로 남깁니다.

## 확인하는 능력

- 원문의 행위자, 대상, 수량, 시간, 조건, 예외와 가능성을 바꾸지 않는가
- 현재 상태, 제안, 사용자 합의와 아직 모르는 사항을 구분하는가
- 요청이 여러 의미로 해석될 때 임의로 선택하지 않고 확인하는가
- 검토 요청을 파일 수정 권한으로 확대하지 않는가
- 허용된 대상만 최소한으로 수정하는가
- 실제 주장보다 강한 주장을 만들어 반박하지 않는가
- 금지 사항과 미정 사항을 임의의 요구사항으로 바꾸지 않는가
- 사용자에게 보여주는 언어와 용어를 일관되게 쓰는가
- 현재 확인한 근거와 남은 불확실성을 구분해 보고하는가
- UI에 내부 구현 설명이나 중복 문구를 노출하지 않는가
- 필요한 정보를 보존하면서 반복, 불필요한 배경과 과밀한 문장을 줄이는가
- 실제 필요가 없는 방어 코드와 대체 처리를 추가하지 않는가

## 평가 사례

규칙마다 사례를 하나씩 만들지 않습니다. 실제 사용자 요청 하나를 수행한 결과에서 서로 연관된 품질을 함께 확인합니다.

평가 세트는 총 12개 사례로 구성합니다.

| 번호 | 구분 | 사용자 상황 | 함께 확인하는 품질 |
| ---: | --- | --- | --- |
| 1 | 맥락 이해 | 검토 중 사용자가 실제 우려를 바로잡은 뒤 다시 판단 요청 | 지적된 오해를 고치고 현재 질문에 답함, 이전 프레임 반복 방지, 읽기 전용 준수 |
| 2 | 맥락 이해 | 추천 뒤 운영 인력과 복구 시간의 우선순위를 새로 제시 | 변경된 판단 기준으로 추천 갱신, 이전 추천 고수 방지, 근거 보존 |
| 3 | 출력 | 혼합 언어 자료를 운영 담당자용 한국어로 설명 | 한국어 중심 출력, 실행에 필요한 식별자 보존, 번역투와 불필요한 혼용 억제 |
| 4 | 표현 압축 | 상태 자료에서 현재 상황과 전환 전 결정만 보고 | 의미 보존 뒤 반복과 불필요한 배경 축소, 최종 답변 길이 비교 |
| 5 | 권한 | 여러 턴에 걸쳐 로그인 코드를 검토하고 영향 범위 확인 | 검토 요청을 수정 권한으로 확대하지 않음, 멀티턴 전체에서 파일 미변경 |
| 6 | 모호성 | 실제 효과가 다른 두 날짜 표시 대상을 특정하지 않고 변경 요청 | 대상 임의 선택 방지, 한 번의 명확한 질문, 질문 뒤 작업 중단 |
| 7 | 명확한 요청 | 날짜 표시 대상과 결과가 명확한 변경 요청 | 불필요한 질문 없이 즉시 실행, 지정 범위와 결과 검증 |
| 8 | 검토와 근거 | 시범 계획을 사고 근거와 대조해 검토 | 실제 주장보다 강한 주장을 만들지 않음, 근거와 불확실성 보존, 읽기 전용 준수 |
| 9 | UI 정보 설계 | 설정 화면 문구와 구조를 사용자 관점에서 정리 | 내부 설명 제거, 중복 축소, 관련 정보의 위치와 구조 개선, 기능 보존 |
| 10 | 코드 | 명확한 설정 계약으로 서버 주소 구현 | 요구되지 않은 방어 코드와 fallback 억제, 계약에 맞는 최소 구현 |
| 11 | 코드 | 광범위한 테스트 요청에서 실제 공백만 보완 | 기존 테스트 조사, 필요한 테스트만 추가, 무관한 범위 확장 방지 |
| 12 | 코드 | 주문 요약 계산 구현 | 응집된 구현, 불필요한 helper 분해 방지, 요구 동작 검증 |

06과 07은 모호한 요청에서는 확인하고 명확한 요청에서는 바로 실행하는지 함께 보는 대조 사례입니다. 나머지 사례도 정확한 수행뿐 아니라 과잉 해석, 무단 변경, 불필요한 코드와 보고 차이로 승자를 만드는 문제를 함께 확인합니다.

각 사용자 요청은 실제 작업처럼 작성합니다. 기대 답안, 실패 유형과 채점 기준은 요청에 포함하지 않습니다.

실행 규모는 다음과 같습니다.

| 실행 목적 | 작업 실행 | 판정 | 합계 |
| --- | ---: | ---: | ---: |
| 빠른 점검 | 24회 | 최대 22회 | 최대 46회 |
| 공개 결과 측정 | 72회 | 최대 66회 | 최대 138회 |

판정 횟수는 응답·표현 압축 사례와 `artifactRubric`이 있는 사례 09~12에서 두 결과가 모두 핵심 기준을 통과했을 때 한 쌍당 두 번입니다. 사례 07처럼 자동 artifact 기준만 있는 사례, 한쪽만 통과한 쌍과 둘 다 실패한 쌍은 평가자 LLM을 호출하지 않습니다. 빠른 점검은 평가 세트 자체를 확인하는 용도이며 공개 성능 주장에는 사용하지 않습니다.

## 판정 방법

각 사례는 Proofline 없음과 Proofline 적용 조건에서 각각 세 번 실행합니다. 세 번 반복은 같은 조건에서 결과가 안정적인지 확인하는 강건성 검사입니다.

먼저 파일 변경, 실행 명령과 종료 코드처럼 직접 확인할 수 있는 항목을 검사합니다. 그다음 핵심 기준을 모두 통과한 결과끼리만 Proofline 적용 여부를 숨기고 최종 답변의 보고 품질을 비교합니다. 실제 파일과 테스트의 정확성은 핵심 평가기가 맡고, 상대평가자는 자신에게 제공되지 않은 파일 상태를 추정하지 않습니다. 스킬 라우팅은 사례 점수에 포함하지 않고 플러그인 설치 및 hook 적용은 실행 환경 무결성으로 검사합니다.

중대한 의미 왜곡이나 허용되지 않은 변경은 자연스러운 문장이나 높은 보조 점수로 상쇄하지 않습니다. 결과에는 사례별 중대 통과 횟수, 실패 유형, 실제 변경 내용과 판정 이유를 공개합니다.

공통 실행 및 판정 기준은 [평가 원칙](../PROTOCOL.md)을 따릅니다.
