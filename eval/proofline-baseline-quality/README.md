# proofline-baseline-quality 평가

`proofline-baseline-quality`가 Codex의 기본 작업 품질에 어떤 차이를 만드는지 확인합니다.

같은 요청을 스킬 미적용 상태와 스킬 적용 상태에서 각각 수행하고, 의미 보존과 작업 범위, 실제 파일 변경 및 결과 보고를 비교합니다. 자동 선택으로 조건이 섞이지 않도록 스킬 미적용 조건에서는 대상 스킬을 사용하지 말라고 명시하고, 스킬 적용 조건에서는 `$proofline-baseline-quality`를 명시적으로 호출한 뒤 작업 전에 전체 `SKILL.md`를 읽도록 요구합니다.

## 실행 범위

평가 세트는 정상 동작 4개와 부정 사례 3개, 총 7개로 구성되어 있습니다. 읽기와 요약뿐 아니라 코드 수정, UI 문구 수정, 모호한 요청에서의 중단, 읽기 전용 검토, 요구사항 문서 작성과 표현 압축까지 함께 확인합니다.

저장소의 `eval` 폴더에서 다음 명령을 실행합니다.

```powershell
npm install
npm run eval:validate
npm run eval:smoke
```

빠른 점검은 Codex 작업 실행 14회로 구성됩니다. 세 번 반복하려면 `npm run eval:full`을 사용합니다. 작업 결과를 생성한 뒤 `npm run eval:judge`를 실행하면 저장된 `full.json`을 사용해 상대평가만 수행합니다. 결과 화면은 `npm run eval:view`로 엽니다.

공개 결과 파일은 전체 실행과 상대평가가 끝난 뒤 `npm run eval:publish`로 생성합니다. 로컬 절대 경로와 중간 실행 기록을 제외한 `summary.md`, `metadata.json`, `result.json`만 `results/published/<날짜>/`에 저장합니다. `results/local/`은 Git에 포함하지 않습니다.

상대평가는 핵심 기준을 먼저 적용합니다. 한쪽만 핵심 기준을 통과하면 그 결과를 선택하고, 둘 다 통과한 경우에만 `gpt-5.6-sol` 평가자가 추론 강도 `low`로 두 답변을 `미적용/적용`과 `적용/미적용` 순서로 각각 평가합니다. 두 순서의 승자가 다르면 위치 영향을 배제할 수 없으므로 동점으로 처리합니다. 평가자는 동점을 선택할 수 있고 전체 이유와 기준별 이유를 JSON으로 남깁니다.

평가 기준만 수정한 뒤 이미 저장된 원시 결과를 다시 판정할 때는 다음 명령을 사용합니다.

```powershell
npm run eval:regrade
```

재판정은 `results/local/full.json`의 모델 응답을 다시 사용하므로 Codex 작업을 새로 실행하지 않습니다. 원본 결과는 덮어쓰지 않으며 `full-regraded.json`과 `full-regraded-summary.md`를 별도로 만듭니다. 파일 작업 사례를 완전 자동으로 재판정하려면 원시 결과에 평가 대상 산출물 또는 변경 내역이 남아 있어야 합니다.

## 확인하는 능력

- 원문의 행위자, 대상, 수량, 시간, 조건, 예외와 가능성을 바꾸지 않는가
- 현재 상태, 제안, 사용자 합의와 아직 모르는 사항을 구분하는가
- 요청이 여러 의미로 해석될 때 임의로 선택하지 않고 확인하는가
- 검토 요청을 파일 수정 권한으로 확대하지 않는가
- 허용된 대상만 최소한으로 수정하는가
- 실제 주장보다 강한 주장을 만들어 반박하지 않는가
- 금지 사항과 미정 사항을 임의의 요구사항으로 바꾸지 않는가
- 사용자에게 보여주는 언어와 용어를 일관되게 쓰는가
- 현재 확인한 근거와 남은 불확실성을 구분해 보고하는가
- UI에 내부 구현 설명이나 중복 문구를 노출하지 않는가
- 필요한 정보를 보존하면서 반복, 불필요한 배경과 과밀한 문장을 줄이는가
- 실제 필요가 없는 방어 코드와 대체 처리를 추가하지 않는가

## 평가 사례

규칙마다 사례를 하나씩 만들지 않습니다. 실제 사용자 요청 하나를 수행한 결과에서 서로 연관된 품질을 함께 확인합니다.

평가 세트는 **정상 동작 4개와 부정 사례 3개**, 총 7개로 구성합니다.

| 번호 | 구분 | 사용자 상황 | 함께 확인하는 품질 |
| ---: | --- | --- | --- |
| 1 | 정상 동작 | 여러 회의 자료를 경영진용 요약으로 정리 | 의미·조건·시간·가능성 보존, 현재 상태·제안·미정 구분, 자연스러운 한국어, 근거와 불확실성 구분 |
| 2 | 정상 동작 | `null` 세션 로그인 오류를 수정하고 테스트 실행 | 허용된 범위만 수정, 기존 동작 보존, 단순한 코드, 불필요한 방어 처리 억제, 실제 검증과 결과 보고 |
| 3 | 정상 동작 | 설정 화면의 지정된 문구 한 곳을 한국어로 수정 | 정확한 대상만 수정, 다른 사례로 확대하지 않음, UI 문구의 언어 일관성, 중복·내부 설명 억제 |
| 4 | 부정 사례 | 서로 다른 두 설정 저장 방식이 있는 프로젝트에서 “데이터베이스로 바꿔 달라”고 요청 | 모호한 대상을 임의로 선택하지 않음, 한 번의 명확한 질문, 질문 뒤 작업 중단, 파일 미변경 |
| 5 | 부정 사례 | 수정 가능한 작업공간에서 조건과 예외가 있는 이전 계획을 비판적으로 검토 | 읽기 전용 준수, 실제 주장과 예외 보존, 과장된 반박과 동기 추정 금지, 근거·영향·불확실성 보고 |
| 6 | 부정 사례 | 금지 사항과 미정 사항이 섞인 요청을 구현 요구사항으로 정리 | 금지·예외·기존 계약 보존, 미정을 결정으로 바꾸지 않음, 새 요구사항·승인 조건·대체 동작을 만들지 않음 |
| 7 | 정상 동작 | 스레드·성능·기술 부채·작은 모델을 한 번에 설명 | 필요한 설명 보존, 정확한 개념어, 반복·불필요한 배경·예시 억제, 비교하기 쉬운 구조와 목록 유지, 문장 과밀 억제 |

정상 동작 사례에서는 요청한 작업을 정확히 완료하는지 확인합니다. 부정 사례에서는 모호성, 읽기 전용 요청, 금지 사항처럼 잘못된 확장이나 임의 판단을 유발하기 쉬운 조건에서 멈추거나 범위를 지키는지 확인합니다.

각 사용자 요청은 실제 작업처럼 작성합니다. 기대 답안, 실패 유형과 채점 기준은 요청에 포함하지 않습니다.

실행 규모는 다음과 같습니다.

| 실행 목적 | 작업 실행 | 판정 | 합계 |
| --- | ---: | ---: | ---: |
| 빠른 점검 | 14회 | 최대 14회 | 최대 28회 |
| 공개 결과 측정 | 42회 | 최대 42회 | 최대 84회 |

판정 횟수는 두 결과가 모두 핵심 기준을 통과했을 때 한 쌍당 두 번입니다. 한쪽만 통과하거나 둘 다 실패하면 평가자 LLM을 호출하지 않습니다. 빠른 점검은 평가 세트 자체를 확인하는 용도이며 공개 성능 주장에는 사용하지 않습니다.

## 판정 방법

각 사례는 스킬 미적용과 스킬 적용 조건에서 각각 세 번 실행합니다.

먼저 파일 변경, 실행 명령과 종료 코드처럼 직접 확인할 수 있는 항목을 검사합니다. 그다음 핵심 기준을 모두 통과한 결과끼리만 스킬 적용 여부를 숨기고 최종 답변의 보고 품질을 비교합니다. 실제 파일과 테스트의 정확성은 핵심 평가기가 맡고, 상대평가자는 자신에게 제공되지 않은 파일 상태를 추정하지 않습니다.

중대한 의미 왜곡이나 허용되지 않은 변경은 자연스러운 문장이나 높은 보조 점수로 상쇄하지 않습니다. 결과에는 사례별 중대 통과 횟수, 실패 유형, 실제 변경 내용과 판정 이유를 공개합니다.

공통 실행 및 판정 기준은 [평가 원칙](../PROTOCOL.md)을 따릅니다.
