# 평가 원칙

이 문서는 Proofline 평가의 공통 실행 조건과 판정 방법을 설명합니다.

## 1. 비교 조건

모든 사례는 다음 두 격리 환경에서 실행합니다.

| 조건 | 환경 |
| --- | --- |
| Proofline 없음 | 새 `CODEX_HOME`, Proofline 플러그인 미설치, Proofline hook 없음 |
| Proofline 적용 | 별도의 새 `CODEX_HOME`, 현재 저장소에서 고정한 Proofline 플러그인 설치, `SessionStart` hook 실행 |

두 조건의 사용자 프롬프트는 같은 `prompts/task.txt`를 사용하므로 바이트 단위로 같습니다. 프롬프트에 스킬 사용 또는 금지 문구를 넣지 않습니다. 조건 차이는 격리된 Codex 환경에만 둡니다.

적용 조건은 평가용으로 고정한 로컬 플러그인을 설치한 뒤 고정된 두 hook의 신뢰 상태와 Codex의 자동화 전용 hook 신뢰 우회 플래그를 함께 사용합니다. 임의의 외부 hook을 허용하는 용도가 아니며, 실행 전에 설치본의 plugin manifest, hook, baseline skill 해시가 고정 입력과 일치하는지 검사합니다.

## 2. 고정하는 항목

두 조건에서 다음 항목을 같게 유지합니다.

- 사용자 요청과 사례별 작업 파일
- 작업 모델 `gpt-5.6-sol`과 추론 강도 `medium`
- sandbox, 승인, 네트워크와 웹 검색 설정
- Codex CLI와 Codex SDK 버전
- 반복 횟수

Promptfoo의 조건별 설정은 `CODEX_HOME` 선택과 적용 조건의 hook 실행 설정에만 사용되며 사용자 프롬프트에 포함되지 않습니다.

멀티턴 사례의 턴 배열은 `vars`에 두지 않습니다. 사례 metadata에 원문 배열을 보존하고 `beforeEach`에서 JSON 문자열 하나로 직렬화해 provider context에 넣은 뒤 provider가 다시 배열로 복원합니다. 따라서 Promptfoo의 배열 변수 확장으로 한 사례가 턴별 테스트로 분리되지 않습니다.

## 3. 실행 격리

각 조건과 반복은 새 Codex 세션과 새 작업공간에서 시작합니다. 작업공간에는 해당 사례의 fixture만 복사하며 Proofline 스킬을 직접 배치하지 않습니다. 사용자 Codex 설정, 사용자 설치 플러그인, 이전 대화와 다른 사례 결과는 가져오지 않습니다. 로그인 파일은 모델 호출에 필요한 경우에만 격리 홈으로 복사합니다. 격리 홈에는 상위 평가 패키지의 모듈 형식이 플러그인 hook에 전파되지 않도록 CommonJS 경계를 둡니다.

사례 05는 각 사용자 턴 전후의 전체 프로젝트 파일 해시 snapshot과 턴 실행 중 filesystem write event를 함께 기록합니다. 성패는 각 턴 snapshot과 최종 workspace diff로 판정합니다. 쓰기 event가 있어도 턴 종료 전에 원복되어 snapshot과 최종 diff가 깨끗하면 통과하며, event는 `observed`·`reverted` 보조 증거로 남깁니다. artifact 사례는 fixture와 최종 작업공간의 diff 및 변경 파일 전후 내용을 상대평가와 재판정에 사용할 증거로 저장합니다.

동시 실행 수는 1입니다. 고정 순서가 세션이나 작업공간을 섞지는 않지만, 전체 실행 시간 동안 모델 동작이 변할 가능성은 별도로 제거하지 않습니다.

## 4. 실행 전 검사

`eval:validate`는 모델을 호출하지 않고 다음 항목을 검사합니다.

1. 두 조건이 같은 프롬프트 파일을 참조하는지 확인합니다.
2. 사례 점수에 스킬 라우팅 검사가 없는지 확인합니다.
3. 작업공간 준비 코드가 로컬 Proofline 스킬을 복사하지 않는지 확인합니다.
4. 현재 저장소의 plugin manifest, hook, skills를 평가용 로컬 marketplace에 고정합니다.
5. 새 적용군 `CODEX_HOME`에 그 플러그인을 실제 설치하고 설치본의 핵심 파일 해시를 확인합니다.
6. 미적용군 설정에 Proofline 항목이 없고 적용군 설정에 평가용 Proofline 플러그인이 활성화됐는지 확인합니다.
7. Promptfoo 설정과 모든 사례별 핵심 평가기를 검증합니다.

`eval:smoke`와 `eval:full`에서는 두 조건에 전달된 사용자 턴 배열이 같은지 다시 확인합니다. 또한 적용군의 실제 `SessionStart`에서 설치된 `load-baseline.js`가 호출되어 종료 코드 `0`으로 끝났는지, 미적용군에 Proofline이나 사용자 전역 상태가 노출되지 않았는지 검사합니다. 이 조건 무결성 검사를 통과하지 못한 실행은 사례 점수와 무관하게 실패합니다.

## 5. 반복 횟수

| 실행 목적 | 조건별 반복 | 작업 모델 호출 |
| --- | ---: | ---: |
| 빠른 점검 | 1회 | 24회 |
| 공개 결과 | 3회 | 72회 |

세 번 반복은 같은 사례와 조건에서 결과가 안정적으로 나오는지 확인하기 위한 강건성 검사입니다. 숨은 사례에 대한 일반화나 통계적 모집단 추정을 뜻하지 않습니다.

## 6. 판정

각 사례는 사례별 핵심 평가기로 의미 보존, 작업 범위, 실제 파일 상태, 실행 명령과 검증 결과를 판정합니다. 스킬 라우팅이나 스킬 파일을 읽은 흔적은 사례 점수에 포함하지 않습니다. 플러그인 설치와 hook 적용 여부는 조건 무결성 검사에서 다룹니다.

한쪽만 핵심 기준을 통과하면 그 결과를 선택하고 둘 다 실패하면 동점으로 처리합니다. 둘 다 통과한 뒤의 판정 근거는 사례 유형에 따라 다릅니다.

- 응답 사례는 저장된 응답을 A/B와 B/A 두 순서로 비교합니다.
- 사례 04는 두 응답을 서로 보여주지 않고 필수 의미 PASS/FAIL을 독립 판정합니다. 둘 다 의미 PASS인 반복만 최종 답변 글자 수 비교에 포함하며, 제외된 반복과 이유를 별도로 기록합니다.
- 사례 09~12는 최종 보고를 상대평가자에게 주지 않고, 수집한 실제 변경 artifact를 각 사례의 `artifactRubric`으로 A/B와 B/A 비교합니다.

순서 교차 평가에서는 두 순서가 같은 실제 후보를 선택할 때만 승리로 인정하고, 판정이 달라지거나 의미 있는 차이가 없으면 동점으로 처리합니다.

상대평가자에게 어느 후보가 Proofline 적용 결과인지, plugin 또는 skill 본문을 알려주지 않습니다. 표현 압축과 artifact 평가는 해당 사례의 저장된 증거만 사용합니다.

## 7. 결과와 근거

각 실행에서 다음 정보를 수집합니다.

- 최종 답변
- 명령, 종료 코드와 도구 실행 내역
- 생성, 수정, 삭제된 파일 상태
- 사례 05의 턴별 workspace snapshot과 filesystem write event
- artifact 사례의 변경 파일 전후 SHA-256과 UTF-8 내용
- 사례별 핵심 판정과 이유
- 표현 압축 포함·제외 여부와 제외 이유
- 입력, 출력, 캐시와 추론 토큰 사용량

공개 결과에는 평가 세트 버전, 플러그인 버전, plugin manifest·hook·baseline skill SHA-256, 모델과 추론 강도, Promptfoo·Codex SDK·Node.js 버전, 반복 횟수, 원시 결과 SHA-256과 사례별 결과를 기록합니다.

검증하지 못한 실행은 성공이나 실패로 채점하지 않고 미검증으로 남깁니다. 공개 결과는 해당 사례와 반복 범위에만 적용하며 모든 작업에서의 일반적 우위를 의미하지 않습니다.
