# 스킬 프롬프트 작성 원칙

이 원칙은 `skills/` 아래의 스킬 본문, reference, 예시와 호출 메타데이터를 만들거나 수정할 때 적용한다. 목표는 문장 수를 줄이는 것이 아니라, 필요한 행동 변화는 유지하면서 불필요한 컨텍스트 비용과 반복 추론을 없애는 것이다.

## 성능·비용 계약

Proofline 최적화의 목표는 최저 토큰 사용량이 아니라 **무스킬 대비 품질 우위를 최소한의 추가비용으로 얻는 것**이다. 품질은 제약조건이고 비용은 그 제약을 통과한 후보 사이의 최적화 대상이다.

- 복잡하거나 실패 위험이 큰 대상 작업에서는 무스킬 실행보다 성공률이나 결과 품질이 실질적으로 높아야 한다.
- 스킬이 품질을 더 높일 여지가 작은 단순 작업에서는 무스킬과 동등한 품질을 유지하고 추가비용을 작게 제한한다.
- 기존 스킬보다 비용이 낮아도 성공률, 요구 충족, 범위 보존, 검증 신뢰도가 나빠진 후보는 채택하지 않는다.
- 스킬 자체의 Gate 통과나 자기 보고만 품질 근거로 사용하지 않는다. 고정된 외부 검증기, 결과물 검사 또는 블라인드 평가로 실제 결과를 판정한다.
- 캐시 입력, 비캐시 입력, 캐시 쓰기, 출력과 실제 API 등가 비용을 분리하고, 최상위 작업과 모든 하위 작업의 사용량을 합산한다.

벤치마크는 같은 작업·모델·추론 수준·환경에서 무스킬과 스킬 실행을 비교한다. 대표 사례에는 단순 정상 경로, 여러 구성요소가 연결된 작업, 실패 후 복구 경로를 포함하고, 품질을 통과한 실행끼리 정상 경로와 조건부 실패 경로의 비용을 따로 비교한다.

하나의 벤치마크 실패는 수정 가설을 제공할 뿐 보편 규칙을 증명하지 않는다. 특정 사례를 통과시키기 위해 작업 요구, 허용 명령, Gate 또는 외부 검증 기준을 후보별로 바꾸지 않는다. 검증기가 유효한 결과를 거부하거나 실환경과 다른 준비 상태를 제공한 경우에만 벤치마크 결함을 수정하며, 같은 수정본으로 모든 비교 대상을 다시 평가한다.

비용 원인은 역할 합계만으로 판단하지 않는다. 작업 ID와 재개 차수별로 사용량을 나누고, 고정 지침, 탐색·계약 작성, 구현, Gate, 검토, 재작업, 최종 반영 중 어느 구간이 증가분을 만들었는지 확인한다. 구조 변경은 여러 대표 사례에서 품질 제약을 다시 통과하고 총비용을 낮춘 뒤 채택한다.

## 원칙

1. **모델이 이미 안정적으로 수행하는 내용은 쓰지 않는다.** 일반적인 모델 역량, Codex 기본 지침, 저장소 지침과 겹치는 설명은 제거한다. 스킬에는 해당 도메인에서 새로 필요한 지식, 선택 기준, 반복해서 관찰된 실패의 교정만 둔다.
   - 하위 작업 전달문에는 해당 작업이 이미 상속받는 시스템·개발자·프로젝트·`AGENTS.md` 지침을 복사하거나 요약하지 않는다. 전달문은 역할별 고정 계약과 이번 배정에서 새로 생긴 값만 담는다.
2. **같은 의미는 한 곳에만 둔다.** 하나의 요구사항에는 하나의 권위 있는 위치를 정한다. 본문, reference, 예시와 다른 스킬에 같은 규칙을 되풀이하지 않는다. 조건부 세부사항은 reference로 옮기고 본문에는 언제 읽는지만 남긴다.
3. **행동을 바꾸지 않는 문장은 통째로 삭제한다.** 문장을 짧게 고쳐 남기기보다, 그 문장이 없을 때 결과·판단·도구 사용·허용 범위가 달라지는지 확인한다. 달라지지 않으면 문장 전체를 제거한다.
4. **원하는 행동과 결과를 긍정형으로 쓴다.** 금지 사항을 길게 나열하기보다 모델이 선택해야 할 행동, 유지해야 할 정보와 도달해야 할 상태를 직접 쓴다. 반복해서 발생한 고위험 실패처럼 금지 자체가 필요한 경우에만 부정형을 둔다.
5. **모든 작업에 필요한 내용만 본문에 둔다.** 스킬이 호출될 때마다 필요한 핵심 절차와 판단 기준만 `SKILL.md`에 둔다. 특정 작업 유형에만 필요한 UI, 코드, 도구, 형식과 상세 예시는 필요한 때만 읽는 reference나 실행 가능한 script로 분리한다.
6. **과정보다 관찰 가능한 결과를 서술한다.** “다시 읽어라”, “검사하라”, “충분히 검토하라”처럼 범위가 없는 내부 과정을 요구하지 않는다. 대신 최종 산출물이 만족해야 할 상태, 판단에 반영할 근거, 허용된 변경 범위와 실패 조건을 쓴다. 특정 순서나 도구가 결과의 정확성에 필수일 때만 과정을 지시한다.
7. **문장이 유발하는 컨텍스트 비용까지 센다.** 프롬프트 자체의 토큰 수뿐 아니라 각 문장이 새로 읽게 만드는 파일·대화 이력·검사 범위를 비용에 포함한다. 이 비용에 Slice 수와 재시도 가능 횟수를 곱해 정상 경로와 조건부 실패 경로를 따로 평가한다. 변경되지 않은 근거는 재사용하고, 실패할 때만 필요한 세부 절차는 조건부 reference로 분리한다.
8. **하나의 코드 상태에는 하나의 증거를 사용한다.** 성공한 읽기·검색·Gate·검토 결과는 관련 상태가 바뀔 때까지 재사용한다. 큰 출력은 전체를 다시 요청하지 않고 경로, 통계, 정확 검색, 작은 범위 순으로 좁힌다. 완료 검증은 구현 전에 위험도별 예산 안의 최소 집합으로 고정하고, 구현 중 피드백·하위 Gate·합산 검증·최종 적용에서 같은 검사를 되풀이하지 않는다. 기계적 검증이 없는 경계에는 대체 검사를 발명하지 않는다.
9. **분리는 비용을 상쇄할 때만 한다.** 파일·계층·기술이 다르다는 이유로 작업을 나누지 않는다. 별도 작업이 문맥, 의존성, 실패 격리 또는 수리 소유권을 실질적으로 개선할 때만 Slice를 만든다. 한 작업이 여러 계층을 한 번에 안정적으로 구현할 수 있으면 분할하지 않는다.

## 수정 절차

1. 교정하려는 실제 실패와 기대하는 관찰 가능 결과를 먼저 적는다.
2. 각 문장이 모델 기본 역량이나 상위 지침과 겹치는지 확인한다.
3. 같은 의미를 가진 문장을 하나의 권위 있는 위치로 합친다.
4. 내부 과정을 요구하는 문장을 기대 결과와 판단 기준으로 바꾼다.
5. 제거해도 행동이 달라지지 않는 문장을 삭제한다.
6. 수정 전후의 실제 토큰 수, 문장이 추가로 불러오는 컨텍스트 범위, Slice·재시도 반복 배수와 대표 사례의 행동을 각각 확인한다. 정상 경로와 조건부 실패 경로를 구분하며 문장이나 단락 수 감소만 압축 근거로 사용하지 않는다.

## 유지 여부 판정

문장을 남기려면 다음 중 하나를 구체적으로 답할 수 있어야 한다.

- 어떤 기대 행동이나 결과를 만든다.
- 어떤 관찰된 실패를 막는다.
- 어떤 도메인 지식, 계약 또는 도구 사용법을 제공한다.
- 어떤 선택의 자유도를 의도적으로 제한한다.

어느 항목에도 해당하지 않으면 삭제한다.
